# 321Team

**321Team**은 하이브리드 클라우드 컨테이너 플랫폼 설계 및 구현 9기 과정의 프로젝트 팀입니다. 온프레미스와 AWS를 연결해 **이상금융거래 탐지 시스템(FDS)의 교육용 PoC**를 완성했습니다.

## FDS 서비스

FDS는 거래 정보에서 정해 둔 규칙에 해당하는 위험 징후를 찾아 판정 결과와 근거를 기록하는 시스템입니다. 거래 API가 요청과 기존 이력을 확인한 뒤 탐지 엔진에 판정을 요청합니다. 엔진이 결과를 반환하면 거래 API가 거래 내역과 판정 결과를 PostgreSQL에 저장합니다. **DB에 직접 접근하는 앱은 거래 API이며, 탐지 엔진은 DB에 직접 접근하지 않습니다.**

이번 PoC는 거래 판정과 근거 기록을 제공하는 교육용 서비스입니다. 실제 금융 거래 차단과 금융기관의 운영 적합성 인증은 범위에 포함하지 않았습니다.

## 온프레미스 기반과 클라우드 확장

| 단계 | 완성한 구성 |
| --- | --- |
| Phase 1 | VM과 Kubernetes 기반 온프레미스에 앱, PostgreSQL, Harbor와 배포 및 모니터링 기반을 구성했습니다. Ansible로 서버 설정을 자동화하고 보안 검사를 배포 절차에 연결했습니다. |
| Phase 2 | 두 앱의 실행 환경을 AWS의 관리형 OpenShift인 ROSA HCP로 확장했습니다. DB와 Harbor는 온프레미스에 유지하고 AWS EC2 중계 서버와 Libreswan IPsec VPN으로 연결했습니다. |

거래 API의 DB 접속과 워커 노드의 Harbor 이미지 다운로드를 구분했습니다. 사용자 Ingress와 내부 VPN, 배포 관리 API의 목적에 맞춰 접근 범위를 정하고, 워커 노드는 Private Subnet에 배치했습니다.

Harbor를 주 이미지 저장소로 사용하고 ECR은 수동 대체 경로로 구성했습니다. 자동 복제나 자동 전환은 포함하지 않았으며, ECR 전환으로 VPN과 DB 장애까지 복구하는 구성은 아닙니다.

## DevSecOps와 배포 통제

Trivy에서 HIGH 또는 CRITICAL 취약점을 검출하거나 검사 자체가 실패하면 이미지 등록과 배포를 중단하도록 구현했습니다. 취약점 조치 후에는 앱의 빌드와 기동, 이미지 검사를 다시 확인했습니다.

배포 프로그램은 승인한 이미지와 구성 원본, 대상 환경 및 작업창을 대조하고 정해진 앱 리소스만 변경합니다. 요청 결과가 불명확하거나 실제 상태가 예상과 다르면 추가 변경을 멈추고, 남은 작업을 자동으로 반복하지 않도록 했습니다. 작업과 진행 이력을 남겨 운영자가 실제 상태와 대조하고 다음 조치를 판단할 수 있게 했습니다.

이미지 저장소와 관리 API에는 TLS 인증서 검증을 적용했습니다. 앱 실행 권한과 네트워크 접근, 배포 계정의 변경 범위도 제한했습니다. 단일 AZ의 워커 배치를 다중 AZ 고가용성이나 무중단 SLA로 확대하지 않았습니다.

## 프로젝트에서 중요하게 본 가치

- **무결성:** 이미지와 배포 대상, 구성 파일을 검토한 원본과 대조할 근거를 남겼습니다.
- **재현성:** 패키지 버전과 구성 원본을 고정해 같은 입력을 다시 확인할 기반을 마련했습니다.
- **추적성:** 작업 의도와 진행 단계, 사용한 원본의 이력을 연결했습니다.
- **이식성:** 공통 배포 구성과 환경마다 달라지는 설정을 분리했습니다.
